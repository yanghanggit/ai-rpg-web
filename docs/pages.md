# 页面结构与交互

> 定位：记**当前**有哪些屏幕与浮窗、各自负责什么，以及**跨页面的设计口径**。
> 排版参数、组件名、接口路径随实现变，不写在这里：目录 / 命名见 [开发规范](conventions.md)，接口见 [API 使用规范](api-layer.md)。
> 只做桌面，最小支持宽度 1024px。

## 路由表

| 路由 | 页面 | 职责 |
| ------ | ------ | ------ |
| `/` | `LaunchPage` | 启动屏：服务器地址与连接状态，与玩家身份无关 |
| `/lobby` | `LobbyPage` | 玩家入口：玩家名（自动生成）+ 选蓝图并看详情，登录 → 新游戏 |
| `.../home` | `HomeOverviewPage` | 家园：**功能按钮 + 场景卡片**两块（角色信息 / 蓝图信息 / 实体浏览器 / 道具管理 / 叙事 / 副本 / 登出） |
| `.../dungeon` | `DungeonOverviewPage` | **副本总览（备战）**：生成副本、查阅静态数据、编队名单、决定是否出征；不承担副本内流程 |
| `.../dungeon/map` | `DungeonMapPage` | **副本进行中 · 地图**：**房间之间那一站**（进入副本的落点、房间结束后的归处）。唯一能改变队伍位置的地方 |
| `.../dungeon/room` | `DungeonRoomRoute` | **副本进行中 · 房间**：取当前房间，按 `room.type` 分发到开场 / 战斗房间页 |
| `/dev` | `DevIndexPage` | 开发索引（仅 dev）：常用深链 |

## 公共约定

- 路由表在 `src/App.tsx`，Provider（QueryClient / Router）在 `src/main.tsx`。
- **游戏页一律带会话参数**（`/game/:userName/:gameName/...`）：地址即状态，可深链到任意一层。
- 领域逻辑与跨接口编排放 `src/features/<domain>/`；组件归属与依赖方向见 [开发规范](conventions.md)。
- 同一列表里的卡片共用一组栅格参数（如副本卡与角色卡），宽度自然对齐。

## 独立屏幕 vs 浮窗

判据是「这一步要不要离开当前上下文」：

- **独立屏幕**：内容会长、或本身就是一组流程。目前只有**副本**四张屏——总览（备战）→ 地图（房间之间）→ 房间（开场 / 战斗）。
- **什么进 URL**：**导航**进 URL（地图与房间是玩家来回走的目的地，要能刷新、能深链）；**房间类型与战斗阶段不进 URL**——它们是服务端字段算出来的屏幕内派生状态，加路由等于给同一状态找第二个真值来源（同 `combatPhase`、`seedMockFromUrl`）。
- **浮窗**：一处信息、或一步操作，关掉就回到原处。统一用 `components/Modal.tsx`（自实现遮罩：遮罩是真的 `<button>`、ESC / 点遮罩 / ✕ 关闭、焦点与滚动处理）。**不用原生 `<dialog>` + `showModal()`**——jsdom 未实现，用了就没法做组件测试。

## 浮窗层级

- **一级**：角色信息、场景信息、蓝图信息、实体浏览器、道具管理、副本操作、地图、进入副本确认、全部叙事、奖励、队伍牌组、战斗手牌、战斗牌堆、登出确认。
- **二级**：选时装、合成确认、队伍牌组里某人的牌组、战斗手牌里某张卡、战斗里点开的某个牌堆。**三级**：卡牌详情——**两栏**：左栏「这张卡原样」（词缀缩略成 `[名称]`）、右栏「完整信息」（说明全文 + **每一枚标记**逐条全文：布尔属性一节、三种时机词缀各一节）；点左栏某枚标记定位并高亮右栏对应那条（色调与卡面同一套，**此时不弹 tooltip**——全文已在眼前）。
- **卡面上的标记 chip（三种时机词缀 + 五个布尔属性）一律可点**，行为同一：弹一枚说明小浮层（“这是什么”），不受祖先 `overflow` 裁切。布尔属性在数据里只有 `true/false`，所以那五句说明是**前端自带的文案**（镜像后端 `card.py` 的字段注释，后端改了机制要回来对齐）。
- **“点整卡”的含义随处境变，所以每一处必须是明确的**：战斗手牌里是「选中待出」，牌组 / 奖励里是「打开详情」。正因为如此，**手牌里看详情要另给一颗「查看」**，不把两个动作叠在同一次点击上。
- 下层开着时上层的 ESC **不响应**——否则一次 ESC 会连关多层。
- **卡牌列表浮窗（牌组 / 手牌 / 牌堆）是同一个组件、同一个尺寸**：`features/cards/CardListDialog`（`Modal` 的 `size="cards"`）——宽正好三张卡、高正好三行（`--card-list-w` / `--card-list-h`），多出来的在框内滚动。**尺寸不跟着卡数走**：两张牌、九张牌、一张没有，打开来都是同一个框（卡少就空着，空牌堆把那句空态摆正中）。卡面用的是**短边足迹**（`--card-list-card-h`），一行三张、行高一致——竖牌足迹三行 ≈ 940px，比一般笔记本的视口还高，会被屏幕压住。
- **同类切换不叠第三层**：从场景浮窗点角色 → 关场景浮窗、开角色浮窗（实体浏览器同理），永远没有「这次 ESC 该关哪层」的歧义。
- 入口与浮窗内容**由页面接线**（`features/` 之间不互相依赖）；同一个浮窗给多页用靠**能力开关**区分（如 `craftEnabled`），不拆成两个组件——拆开会让共用渲染逻辑出现两份。

## 进入副本（出征）

客户端第一个**不可逆**的动作：

- **入口在副本卡片的操作行**（不是工具栏）。确认框摊开**队伍**（带 HP / ATK / DEF）、背包与起点房间——因为名单是在**确认那一刻**才固化的，此后不能再改。
- 队伍里有死亡角色会让后端断言失败（500）→ 确认框提前禁用「确认进入」并写明原因。
- 成功后落到**地图**（"还没进第 1 间"那一种状态）。
- 同一时间只能有一个副本在跑；进行中时总览页「进入副本」禁用、只剩「回到副本」——那只是**异常落点的兜底**（返回键 / 地址栏才能站在总览页），落点是队伍所在的那间房。
- **房间类型标签只有一处实现**（`readDungeonInfo`）：`opening` → 开场、`combat` → 战斗；`opening` 指"进入副本后的**起点**"，不是打法描述。

## 副本进行中（房间 + 地图）

副本内是**两张屏**：**房间**（当前房间的正文）与**地图**（**房间之间那一站**）。这个切法由**副本的基本规律**推出，不是排版偏好：

- **副本只向前**：`current_room_index` 只在「进入副本」置 0、在「推进」+1，**没有任何接口能回退** → 只有「前进」与「放弃离开」，**没有"返回"**。
- **地图在服务端不存在**：进入 / 推进都把队伍放进当前房间的 stage。"站在地图上"纯粹是客户端视图——所以「进入房间」零服务端调用，唯一真正的移动是「离开副本」。
- **地图 = 唯一能改变队伍位置的地方**：房间在"位置"上只读（结束动作只负责结束本间、把队伍送到地图）；`advance_stage` 只发生在地图。今天下一间是**唯一**候选，但它是那个接缝——将来长成"选路"时，长出来的就是这里。
- **地图只有三种状态**：刚进入副本、两间之间、没有可前往的房间（通关 / 打输的兜底）。**战斗没结束时地图不该出现**（队伍就在那间房里），所以整页把这种落点**转发**回房间——正常流程走不到，URL / 收藏 / 返回键到得了。
- **动作长在目标那一行**：地图页清单与「地图」浮窗是**同一个组件**（`DungeonRoomList`），差别只有行尾那颗按钮——**按钮摆在哪一行，就同时说明了"能去哪"与"只能去哪"**（将来选路＝多行各带一颗）。
- **房间没有出口**：房间页不提供"回到地图"，只有**它自己的结束动作**（开场房 / 战斗房各有措辞与条件）；「副本操作」在任何一屏都只有 叙事 / 离开副本。
- **结束本间之后**：还有下一间 → 地图；**没有下一间、或打输了 → 直接离开副本回家园**。
- **已结束的房间进不去**：地图上那一行不再带按钮，自然回不了头——不需要另写规则。代价是**未领的开场奖励 / 未收的战斗战利品永久失去**（服务端把两者都绑在"当前房间"上），这是**设计要的惩罚**，所以结束动作只**提示、不阻止**（后文两处提醒都出自这一条）。
- **副本内一律 `replace`**：历史栈不留可回退的房间，否则返回键会变成"从房间里溜到地图"的出口。

结构按「变化原因」切开（组件名只作索引，归属见开发规范）：

- **`DungeonRunGate`**（地图 / 房间共用）：只做「取当前房间 → 加载中 / 404 出口」，判据**先看数据、再看状态**（react-query 允许"有数据 + 报错"共存，先判错误会把错误页当成副本第一屏）。
- **`RoomScaffold`**（地图 + 两房间页共用）：标题 + 标题行入口 + 菜单 + 叙事浮层。房间名与「离开副本」都**传进来**（地图不在某间房里）；这层要克制，加进来的必须真的适用于每种房间。
- **`readRoomGuards` + `readNextRoom`**：只回答**本间状态自身**的两件事（结束了没有、有没有下一间）。**「能不能离开 / 推进」不在客户端预判**——一律由服务端拦、原因原样显示，不写镜像就不存在两处口径要同步。
- **目录按语义归属分**：`features/dungeon/{overview,map,opening,combat}/` 各装"属于这一屏 / 这个房间"的东西（动作 hook 也跟屏走），顶层只留被两屏以上（或框架）用到的。

**标题行三个「副本入口」**（只看图标，靠 `aria-label` / `title`）：**副本操作**（叙事 / 离开副本；**战斗房多一行「战斗信息」**，任何阶段都能开；未读叙事信号上提到齿轮上）、**地图**（设定 + 房间清单 + 进度，只读）、**牌组**（队伍名单 → 某人牌面 → 卡牌详情）——**地图页只给后两个**（它自己就是房间清单）。右边还有一颗**本间主行动**（`RoomScaffold` 的 `roomAction`，字形随本间状态变、由页面算，没有就不给）；它的**提醒色是全屏同一条口径**：**再做这一步就会失去什么**时变 `--warn`、后果写进 `title`——与角色卡上的「!」同一件事，只是分别贴着"东西在哪"与"哪一步会失去它"。

**叙事入口只有一个实现**：会话消息是**会话级**资源（本局所有事件，不是某个房间产生的），战斗房一样会追加，所以入口属于共同框架，家园页与副本页共用同一个 hook 与浮层。**未读基线跨屏存活**：已看到第几条存在模块级状态里，不随路由卸载（"进副本 → 打一会儿 → 回家园"后，副本期间的事件在家园页仍显示未读）；当前只在内存里，将来换存储层时调用方不用改。

### 开场房间（`room.type === "opening"`）

这一屏就是**准备**：`初始化 → 生成奖励 → 领卡 → 结束本间`。

- **卡片是这一屏的基调**：横置的**场景卡** + 右边一张横置的**「回到地图」卡**，下面一排**竖置的角色卡**。场景卡与角色卡**共用同一副足迹**（`--card-short × --card-tall`），场景卡只是转 90°；战斗房复用同一对组件。**场景卡固定大小**（换房间、初始化前后都不跳），所以环境叙述超出三行就省略、**全文在「场景信息」浮窗**（点整张卡打开，那里还能点场景内角色）。初始化三态**全在场景卡上**：进行中（不可点）→ 失败（显示原因、点卡重试）→ 就绪（点卡看全文）。
- **本间没有工具栏、标题行也没有主行动**：两个动作都在正文里——「结束本间」是场景行右边那张「回到地图」卡，初始化三态在场景卡上（同一件事只留一个入口）。
- **队伍是一排竖着的角色卡**：名字 + 属性（`HP x/y · 攻 n · 防 m`，与战斗房同一份措辞）+ `卡组 N`，整卡可点开角色信息。**牌组不在这层开口子**（标题行「牌组」已能看全队，两个入口迟早各自演化）。
- **奖励入口是卡底同一颗按钮的三态**：生成奖励 → 获取奖励 → 查看奖励；候选不摊在页面上，点开浮窗才看到（每张一个「挑选」，不做二次确认）。**「生成奖励」长在每张卡上，却只算一件事**：后端一次给**全队**挂奖励组件，点哪张都是同一次调用；领取 / 查看才按成员各自。
- **结束本间是一扇单向门**：按下即回地图（**不**推进副本），本间此后进不去；还有奖励没领时**只提醒不阻止**——卡底按钮与「回到地图」卡都变提醒色（判据同为 `hasUnclaimedRewards`，见上）。
- **初始化自动跑一次**（失败留给玩家手动重试）——服务端硬前置：未初始化时既不能推进也不能退出。
- **不走家园那套**：副本进行中家园接口一律被拒，所以这屏没有道具管理（背包在家园页看），也不提供「返回副本总览」。

### 战斗房间（`room.type === "combat"`）

- **正文由战斗阶段派生**（初始化 / 回合开始 → 行动 → 结算），在**同一屏内换面板**，阶段不进 URL。"初始化"与"回合开始"共用**开局准备屏**（`CombatSetupPanel`）：上面敌人、中间场景卡 + 「开始」卡、下面队伍（与开场房**共用 `StageCard` / `ActorCard`**）。**进入战斗房间自动初始化一次**（失败不自动重试）。**「开始」卡是这屏唯一的动作**：点它开第一回合（`draw`）；init 未成功时它也是重试入口；开局后改成「开始新回合」。
- **行动面板（`turn`）**：
  - 上面一条**参战者横滑名单**，**顺序就是 `action_order`**（已行动置灰 / 当前绿框 / 待行动）——名单本身就是顺序条；每格 = 身份 / HP 攻防 / 能量 / 总格挡 / 手牌摘要。
  - 下面三栏：左 = 当前行动者资源（HP / 能量 / 总格挡 / 抽牌堆），中 = 手牌横滑，右 = 「过牌」+ 消耗 / 弃牌堆。
  - **三个牌堆都是按钮**（抽牌堆 / 消耗牌堆 / 弃牌堆）：点开是这一撑的**卡牌列表**，与手牌 / 牌组共用 `CardListDialog`（只是换标题与内容，`owner` = 当前行动者，所以【塞牌】照样认得出）。圆柱里那个数字就是张数，按钮的无障碍名里也带着（「查看抽牌堆（4 张）」）。它们与同列的 HP / 能量 / 格挡不同——那三个是只读的，所以只有牌堆独占一颗完整描边。
  - **出牌 = 两次选择 + 一次确认**：点手牌 → 那张牌**上移**（再点缩回）；点名单里的角色 → 那张卡**下移**（再点缩回）；两次都齐，中间才长出「出牌」并真的发请求（出牌条就占中列顶部那个空位：左提示矩形 + 右几颗卡状按钮「查看 / 出牌 / 取消」，与开场房「回到地图」卡同族）。自身牌选中后**自动**压下本人；`all`（阵营全体）/ `spread`（阵营散射）选中一个锚点即**整阵营**压下（客户端按锚点阵营提前算，与服务端 `resolve_targets` 同口径；发请求仍只发锚点），`spread` 只在提示里多一句「（在以上目标中随机）」。选目标态下点名单卡只**选 / 取消目标**，不再弹角色信息。**手牌里整卡点击就是「选中」**，所以「看这张牌的详情」另给中间那颗「查看」（非手牌那几处是整卡直开详情）。
  - **怪物回合共用同一版面**：手牌只读、右下那颗换成「推进怪物回合」。
  - 名单卡还挂两个**只读**入口：点整张卡开**角色信息**，点卡底那行**平铺的文本**开**手牌**（只给数量：`手牌 N` + `[被动] N`；敌方另加 `[塞牌] M` = 手牌里来自我方阵营的牌数）。
  - **卡面**：不出现【塞牌】（那是"牌与持有者的关系"，只挂在角色卡一侧）；布尔属性（消耗 / 保留 / 虚无 / 可传递 / 不可出牌）与三种时机词缀统一成一排**带色 chip**；来源只在"不是自己的牌"时显示且上色。
- **战斗页只留"现在该做什么"**：宏观状态（状态 / 结果 / 回合）与引导句都不常驻，收进 ⚙「副本操作」的「战斗信息」（战斗房每个 phase 都有这一行）。点开是三层：上面一排状态事实 → 中间按阵营分两段的**参战者名字**（横着排、自动换行，战死的名字置灰 + 挂「已战死」；这里**不筛死者**，与行动面板相反）→ 下面全部回合的 `Round` 明细；**本回合记录同样不常驻页面**。
- **结算态的结束动作就在标题行那颗图标上**（战斗房是 `roomAction` 唯一的使用者），未收的战利品**只提醒不阻止**；没打完时那个槽位空着。
- **阶段机有唯一实现**（`combatPhase` / `readCombat`）：屏幕只按它给的阶段渲染，不自己判 `state` / `result` 的组合。
