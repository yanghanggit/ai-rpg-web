# 页面结构与交互

> 定位：记**当前**有哪些屏幕与浮窗、各自负责什么，以及**跨页面的设计口径**（为什么这样切）。
> 具体的排版参数、组件名、接口路径随实现变，不写在这里：目录 / 命名 / 依赖见 [开发规范](conventions.md)，
> 接口用法见 [API 使用规范](api-layer.md)，排版基线见 [开发规范 §五](conventions.md)。
> 本项目只做桌面，最小支持宽度 1024px。

## 路由表

| 路由 | 页面 | 职责 |
| ------ | ------ | ------ |
| `/` | `LaunchPage` | 启动屏：服务器地址与连接状态，与玩家身份无关 |
| `/lobby` | `LobbyPage` | 玩家入口：玩家名（自动生成）+ 选蓝图并看详情，登录 → 新游戏 |
| `.../home` | `HomeOverviewPage` | 家园：**功能按钮 + 场景卡片**两块（角色信息 / 蓝图信息 / 实体浏览器 / 道具管理 / 叙事 / 副本 / 登出） |
| `.../dungeon` | `DungeonOverviewPage` | **副本总览（备战）**：生成副本、查阅静态数据、编队名单、决定是否出征；不承担副本内流程 |
| `.../dungeon/map` | `DungeonMapPage` | **副本进行中 · 地图**：**房间之间那一站**（进入副本的落点、房间结束后的归处）。唯一能改变队伍位置的地方 |
| `.../dungeon/room` | `DungeonRoomRoute` | **副本进行中 · 房间**：取当前房间，按 `room.type` 分发到开场 / 战斗房间页 |
| `/dev` | `DevIndexPage` | 开发索引（仅 dev）：常用深链 |

## 公共约定

- 路由表在 `src/App.tsx`，Provider（QueryClient / Router）在 `src/main.tsx`。
- **游戏页一律带会话参数**（`/game/:userName/:gameName/...`）：地址即状态，可深链到任意一层。
- 领域逻辑与跨接口编排放 `src/features/<domain>/`；组件归属与依赖方向见 [开发规范](conventions.md)。
- 同一列表里的卡片共用一组栅格参数（如副本卡与角色卡），宽度自然对齐。

## 独立屏幕 vs 浮窗

判据是「这一步要不要离开当前上下文」：

- **独立屏幕**：内容会长、或本身就是一组流程。目前只有**副本**四张屏——总览（备战）→ 地图（房间之间）→ 房间（开场 / 战斗）。浮窗装不下，也容易和家园状态混淆。
- **什么进 URL**：**导航**进 URL（地图与房间是玩家来回走的目的地，要能刷新、能深链）；**房间类型不进 URL**——房间类型（opening / combat）与战斗阶段都是服务端字段算出来的屏幕内派生状态，给它们加路由等于给同一个状态找第二个真值来源（同一条原则见 `combatPhase`、`seedMockFromUrl`）。
- **浮窗**：一处信息、或一步操作，关掉就回到原处。
- 浮窗统一用 `src/components/Modal.tsx`：自实现遮罩（遮罩是真的 `<button>`，不是挂 onClick 的 div）、ESC / 点遮罩 / ✕ 关闭、焦点与滚动处理。**不用原生 `<dialog>` + `showModal()`**——jsdom 未实现，用了就没法做组件测试。

## 浮窗层级

- **一级**：角色信息、场景信息、蓝图信息、实体浏览器、道具管理、副本操作、地图、进入副本确认、全部叙事、奖励、队伍牌组、登出确认。
- **二级**（叠在一级之上）：选时装、合成确认、队伍牌组里的某个人的牌组。
- **三级**（叠在二级之上）：卡牌详情。
- 下层开着时上层的 ESC **不响应**——否则一次 ESC 会连关多层。
- **同类切换不叠第三层**：从场景浮窗点角色 → 关场景浮窗、开角色浮窗（实体浏览器同理），永远没有「这次 ESC 该关哪层」的歧义。
- 入口与浮窗内容**由页面接线**（`features/` 之间不互相依赖）；同一个浮窗给不同页面用，靠**能力开关**区分（如道具管理的 `craftEnabled`），而不是拆成两个组件——拆开会让共用的渲染逻辑出现两份。

## 进入副本（出征）

这是客户端第一个**不可逆**的动作：

- **入口在副本卡片的操作行**（不是工具栏）。确认框先把**队伍**（带 HP / ATK / DEF）、背包与起点房间摊开——因为名单是在**确认那一刻**才固化的，此后不能再改。
- 队伍里有死亡角色会让后端断言失败（500），所以确认框提前禁用「确认进入」并写明原因。
- 成功后落到**地图**（房间之间那一站，此时是"还没进第 1 间"那一种状态）：先看到"本次副本有哪几间、下一间是什么"，再自己走进去。
- 同一时间只能有一个副本在跑。进行中时总览页的「进入副本」禁用，只剩「回到副本」——那只是**异常落点的兜底**（玩家用返回键 / 地址栏才能站在总览页），落点是**队伍所在的那间房**（那里可能还有没收的战利品 / 没领的候选奖励）。
- **房间类型标签只有一处实现**（`readDungeonInfo`）：`opening` → 「开场」、`combat` → 「战斗」。`opening` 的意思是「进入副本后的**起点**」，不是打法描述。

## 副本进行中（房间 + 地图）

副本内是**两张屏**：**房间**（当前房间的正文）与**地图**（**房间之间那一站**）。这个切法由**副本的基本规律**推出，不是排版偏好：

- **副本只向前**：`current_room_index` 只在「进入副本」置 0、在「推进」+1，**没有任何接口能回退**。所以副本内只有「前进」与「放弃离开」，**没有"返回"**。
- **地图在服务端不存在**：进入 / 推进都把队伍放进当前房间的 stage，服务端始终认为你在房间里。"站在地图上"纯粹是客户端视图——所以「进入房间」是零服务端调用，唯一真正的移动是「离开副本」（回家园）。
- **地图 = 唯一能改变队伍位置的地方**：房间在"位置"这件事上是只读的（只能做自己那摊事），结束动作只负责结束本间、把队伍送到地图；「前进」（`advance_stage`）只发生在这里。今天下一间是**唯一**候选，看着像可以省略——但它是那个接缝：将来地图要长成"选路"（多个候选）时，长出来的就是这里，不是房间页。
- **地图只有三种状态**：刚进入副本（还没进第 1 间）、两间之间（本间已结束、还有下一间）、没有可前往的房间（通关 / 打输的兜底）。**战斗没结束时地图不该出现**（队伍就在那间房里，地图此刻唯一能做的"回房间"本来就是它该待的地方），所以整页把这种落点**转发**回房间——正常流程走不到，URL / 收藏 / 返回键到得了。
- **动作长在目标那一行**：地图页的房间清单与「地图」浮窗是**同一个组件**（`DungeonRoomList`），差别只有行尾那颗按钮——**按钮摆在哪一行，就同时说明了"能去哪"与"只能去哪"**（将来选路＝多行各带一颗）。所以既不需要另开一条工具栏，也不需要"本间尚未结束，请先打完"这类说明句。
- **房间没有出口**：房间页不提供"回到地图"，只有**它自己的结束动作**（开场房 / 战斗房各有措辞与条件）；「副本操作」菜单在任何一屏都只有 叙事 / 离开副本。
- **结束本间之后**：还有下一间 → 地图（在那里前进）；**没有下一间、或打输了 → 直接离开副本回家园**（服务端 `advance_stage` 在这两种情况下必然拒绝，终点落在服务端唯一的出口上）。
- **已结束的房间进不去**：本间一结束，地图上那一行就不再带按钮，那一间自然回不了头——不需要另写"禁止重进"的规则。代价是**未领的开场奖励 / 未收的战斗战利品永久失去**（服务端把两者都绑在"当前房间"上），这是**设计要的惩罚**，所以结束动作只**提示、不阻止**。
- **副本内一律 `replace`**：历史栈里不留可回退的房间，否则浏览器返回键会变成"从房间里溜到地图"的出口。

结构按「变化原因」切开：

- **入口门 `DungeonRunGate`**：地图与房间两条路由共用，只做「取当前房间 → 加载中 / 404 出口」。判据**先看有没有数据、再看状态**：react-query 允许"有数据 + 报错"共存（退出副本时 `/room` 被判 404），先判错误会把错误页当成副本第一屏。
- **共同框架 `RoomScaffold`**：地图与两个房间页共用（标题 + 标题行入口 + 菜单 + 叙事浮层）。房间名与「离开副本」都是**传进来的**：地图不在某一间房里（标题只留副本名，也不渲染「地图」——它自己就是房间清单），而离开副本的状态由页面持有（房间的结束动作也可能用到它）。这一层要克制：加进来的东西必须真的适用于每一种房间。
- **判据 `readRoomGuards` + `readNextRoom`**：只回答两件**本间状态自身**的事——本间结束了没有、还有没有下一间（页面与地图共用）。**「能不能离开副本 / 能不能推进」不在客户端预判**：一律由服务端拦，被拒的原因原样显示——客户端不写镜像，也就不存在「两处口径要同步」这件事。
- **房间清单 `DungeonRoomList`**：「地图」浮窗与地图页共用同一份行——"地图页就是它的可交互版"是字面意思，不是比喻。
- **目录按语义归属分**：`features/dungeon/{overview,map,opening,combat}/` 各装"属于这一屏 / 这个房间"的东西（每屏的动作 hook 也跟屏走：地图的 `useAdvanceStage`、战斗的 `useCombatActions`、开场的 `useOpeningActions`），顶层只留被两张以上屏（或共同框架）用到的。判据是语义归属，不是"谁在用"。

**标题行三个「副本入口」**（只看图标，靠 `aria-label` / `title` 说明；三者都是"副本状态"的一部分。**地图页只给其中两个**：它自己就是房间清单，所以没有「地图」）：**副本操作**（叙事 / 离开副本；**当前是战斗房时再多一行「战斗信息」**——状态 / 回合 / 结果写在行尾，点开看全部 `Round` 明细，**初始化 / 回合开始 / 行动 / 结算哪一阶段都能开**；未读叙事信号上提到这颗齿轮上，否则会被菜单吃掉）、**地图**（整体设定 + 房间清单 + 进度，只读——地图页就是它的可交互版）、**牌组**（本次副本的队伍名单 → 某人的牌面 → 卡牌详情）。这三个右边还有一颗**本间的主行动**（`RoomScaffold` 的 `roomAction`）：字形随本间状态变，由页面算——**本间现在该做什么**是房间专属的，框架自己不知道；没有的事就不给（`null`：地图页没有它——前进是页面上的按钮；开场房也没有它——初始化三态与结束本间都在正文卡片上）。它的**提醒色**是全屏同一条口径：**再做这一步就会失去什么**（未领的奖励 / 未收的战利品）时变 `--warn`，后果写进 `title`——与角色卡上的「!」同一件事，只是分别贴着"东西在哪"与"哪一步会失去它"。

**叙事入口只有一个实现**：会话消息是**会话级**资源（本局所有事件，不是某个房间产生的），战斗房一样会追加，所以入口属于共同框架；家园页与副本页共用同一个 hook 与同一个浮层。

- **未读基线跨屏存活**：已看到第几条存在模块级状态里，不随路由卸载——所以「进副本 → 打一会儿 → 回家园」后，副本期间的事件在家园页仍显示未读。当前只在内存里（刷新即重新算）；将来要跨刷新记住，换存储层时调用方不用改。

### 开场房间（`room.type === "opening"`）

这一屏就是**准备**：`初始化 → 生成奖励 → 领卡 → 结束本间`。

- **卡片是这一屏的基调**：横置的**场景卡**（横 = 场景 / 进度）+ 它右边一张横置的**「回到地图」卡**，下面一排**竖置的角色卡**（竖 = 人）。场景卡与角色卡**共用同一副足迹**（`--card-short × --card-tall`），场景卡只是转 90°（横 = `长 × 短`，竖 = `短 × 长`），所以横竖并排是一族。
- **场景卡固定大小**（换房间、初始化前后都不跳；组件 `dungeon/StageCard`，与战斗房共用），所以环境叙述超出三行就省略，**全文在「场景信息」浮窗里**（点整张卡打开，那里还能点场景内角色）。开场房的初始化三态**全在场景卡上**：初始化中显示「进行中…」（不可点）→ 失败显示原因且**点卡重试** → 就绪显示叙述且点卡看全文。
- **本间没有工具栏，标题行也没有主行动**：两个动作都在正文里——「结束本间」是场景行右边那张「回到地图」卡（更好点、更好观察），初始化三态在场景卡上。所以标题行只留三个「副本入口」，`roomAction` 槽位在开场房是空的（同一件事只留一个入口：原来那颗 ↻ / → 与卡片是同一条件、同一动作，属重复）。
- **队伍是一排竖着的角色卡**（组件 `dungeon/ActorCard`，与战斗房共用；与牌面同一套形状）：卡面 = 名字 + 属性（`HP x/y · 攻 n · 防 m`，与战斗房同一份措辞）+ `卡组 N`，整卡可点开角色信息。**牌组不在这层开口子**：标题行的「牌组」入口已经能看全队，两个入口迟早各自演化。
- **奖励入口是卡底同一颗按钮的三态**：生成奖励 → 获取奖励 → 查看奖励。候选不摊在页面上，点开浮窗才看到（每张一个「挑选」，不做二次确认）。
- **「生成奖励」长在每张卡上，却只算一件事**：后端一次给**全队**挂奖励组件，所以点任何一张卡上的它都是同一次调用；领取 / 查看才是按成员各自的。
- **结束本间是一扇单向门**：按下即回地图（**不**推进副本——推进是地图上的动作；本间之后没有房间时改为直接离开副本），本间此后进不去。还有奖励没领时**不阻止**（未领即失去是设计要的惩罚），但两处都提醒：卡底那颗按钮变提醒色 + 「!」（“这里还有东西”），「回到地图」卡也变提醒色（“这一步一按就没了”）——判据就是同一个 `hasUnclaimedRewards`。
- **初始化自动跑一次**（失败留给玩家手动重试）——这是服务端硬前置：未初始化时既不能推进也不能退出。
- **不走家园那套**：副本进行中家园接口一律被拒，所以这一屏没有道具管理（背包在家园页看），也不提供「返回副本总览」。
- **不走家园那套**：副本进行中家园接口一律被拒，所以这一屏没有道具管理（背包在家园页看），也不提供「返回副本总览」。

### 战斗房间（`room.type === "combat"`）

- **正文由战斗阶段派生**（初始化 / 回合开始 → 行动 → 结算），在**同一屏内换面板**，阶段不进 URL。"初始化"与"回合开始"共用**开局准备屏**（`CombatSetupPanel`）：上面敌人、中间场景卡 + 「开始」卡、下面队伍（这类卡与开场房**共用 `StageCard` / `ActorCard`**，所以横竖同尺寸、措辞同来源；战斗只留名字 / 身份 / 一行 HP 攻防，场景卡可点开「场景信息」全文，敌人卡与队伍卡都整卡可点开角色信息）。**进入战斗房间自动初始化一次**（与开场房间同一套；失败不自动重试）。**「开始」卡是这屏唯一的动作**：初始化完成后点它开启第一回合（`draw`）；init 还没成功时它也是重试入口（点它先补 `init`、成功后接上 `draw`）。开局后（已有回合）改成「开始新回合」。
- **行动面板（`turn`）**：上面一条**参战者横滑名单**——**名单顺序就是 `action_order`**（已行动置灰 / 当前绿框 / 其余待行动），所以不另画顺序条；每格是「身份 / HP 攻防 / 能量 / 总格挡 / 手牌受击词缀摘要」（受击词缀口径同怪物 AI 的 `revealed_cards`：带受击词缀的手牌是对手可见的信息）。下面三栏：左是当前行动者的资源（HP 面板 / 能量星 / 总格挡六边形 / 抽牌堆圆柱），中间是手牌横滑，右是「过牌」+ 消耗 / 弃牌堆。**出牌 = 点手牌选中 → 点名单里的角色指定目标**（自身牌选中后点「出牌（自身）」）；**怪物回合共用同一版面**，只是手牌只读、右下那颗换成「推进怪物回合」。**本回合记录不常驻页面**——要看 log 用 ⚙「战斗信息」（结算页仍常驻）。
- **战斗页只留"现在该做什么"**：宏观状态（状态 / 结果 / 回合那排 chip）与第一回合的引导句都不常驻页面——它们收进 ⚙「副本操作」菜单里的「战斗信息」一行（战斗房在**每个 phase** 都有这一行），点开是全部回合的 `Round` 明细（`models/combat.py::Round`）。
- **结算态的结束动作就在标题行那颗图标上**（战斗房是 `roomAction` 唯一的使用者，字形是「离开本间」），未收的战利品同样**只提醒不阻止**（收取按钮与那颗 → 一同变提醒色，后果在 `title`）；没打完时那个槽位空着——还在打就没有"结束本间"可做。
- **阶段机有唯一实现**（`combatPhase` / `readCombat`）：屏幕只按它给的阶段渲染，不自己判 `state` / `result` 的组合。
