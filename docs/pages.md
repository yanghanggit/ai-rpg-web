> 定位：记录**当前**的路由、每个页面负责什么、屏幕与浮窗怎么分工、桌面下的排法。（本项目只做桌面，最小支持宽度 1024px，见 [开发规范 §五](conventions.md)。）

> 全局的目录 / 命名 / 依赖约定见 [开发规范](conventions.md)，接口用法见 [API 使用规范](api-layer.md)。

## 公共约定

- 路由表在 `src/App.tsx`；Provider（`QueryClientProvider`、`BrowserRouter`）在 `src/main.tsx` 装配。
- **游戏页一律带会话参数**（`/game/:userName/:gameName/...`），即「地址即状态」——可直接深链到任意一层。
- 领域逻辑与跨接口编排放 `src/features/<domain>/`，组件放哪、依赖方向见 [开发规范](conventions.md)。
- **布局规则**（`.page` / `.page--wide` 的判据、卡片栅格写法、1024px 基线）属于工程约定，见 [开发规范 §五](conventions.md)；本节只记**各页的排法**：家园页 3 列卡片，入口页左表单右蓝图，开发索引多列，副本页两段各自一行多张，副本房间页多列卡片（奖励候选）。
- 同一列表里的卡片用**同一组栅格参数**（如副本卡片与角色卡片同 `min 320px`），宽度自然对齐。

## 独立屏幕 vs 浮窗

判断标准是「这一步要不要离开当前上下文」：

- **独立屏幕**：内容会长、或本身就是一组流程时用页面（跳路由）。目前是**副本**两张屏：`dungeon`（总览 / 备战：生成、查阅、名单、进入）与 `dungeon/room`（副本进行中）。它们是一组独立流程，浮窗装不下，也容易和家园状态混淆；入口在家园页工具栏，页内各自给「← 返回家园」切回（副本房间页的出口是「离开副本」，见下）。
- **浮窗**：一处信息、或一步操作，关掉就回到原处。
- 浮窗统一用 `src/components/Modal.tsx`：自实现遮罩（遮罩是真正的 `<button>`，不是挂了 onClick 的 div），支持 ESC / 点遮罩 / ✕ 关闭、打开时焦点移入、锁背景滚动。**不用原生 `<dialog>` + `showModal()`**——jsdom 尚未实现，用了就没法做组件测试。

## 浮窗层级

- **一级**：角色信息、场景信息、蓝图信息、实体浏览器、道具管理、副本信息、进入副本确认、全部叙事、牌组、奖励（副本开场）、进入下一关确认、登出确认。
- **二级**（叠在一级之上）：选时装（`StorageCostumeDialog`）、合成确认（`CraftConfirmDialog`）。
- 二级开着时，一级的 ESC **不响应**（用一个「二级状态非空」的守卫拦住 `onClose`），否则一次 ESC 会连关两层。
- **同类切换不叠第三层**：点场景浮窗里的角色 → 关场景浮窗、开角色浮窗；实体浏览器同理（点名字 → 关浏览器、开对应浮窗）。这样永远不会有 ESC 该关哪一层的歧义。
- 入口与浮窗内容之间**由页面接线**（`features/` 之间不互相依赖）：例如副本页的角色卡片只回调 `onSelectActor`，到底开哪个浮窗由页面决定。**同一个浮窗给不同页面用，靠能力开关区分**（如 `ItemManagerDialog` 的 `craftEnabled`），而不是拆成两个组件——拆开会让共用的行渲染逻辑出现两份。

## 进入副本（出征）

这是客户端第一个**不可逆**的动作，单独说清楚：

- **入口在副本卡片的操作行**（不是工具栏）：点开 `EnterDungeonDialog` 做最终确认——**队伍**（玩家 + `PartyRosterComponent` 的成员，带 HP / ATK / DEF）、**背包**（玩家的 `InventoryComponent`）、**起点房间**（`rooms[0]`）。三者由 `useEnterPreview` 一次 details 拿全（名单依赖 `usePartyRoster`）。
- 确认后 `POST /api/home/enter_dungeon/v1/`：**同步**接口（没有 job），成功后跳 `/dungeon/room`。
- 后端在这一刻才把玩家与名单成员固化成 `PartyMemberComponent`，而且**之后不能再改名单**（家园接口全部要求玩家在家园）。所以确认框必须先把名单摊开，而不是点一下就出发。
- **队伍里有 `DeathComponent` 的角色会让后端断言失败（500）**，所以确认框提前禁用「确认进入」并写明原因。
- 同一时间只能有一个副本在跑：`world.dungeon.current_room_index >= 0` 即进行中（退出副本时 `teardown_dungeon` 把它重置回空副本）。进行中时卡片上的「进入副本」禁用，工具栏出现「回到副本」。
- **房间类型标签只写在 `readDungeonInfo`**：`opening` → 「开场」、`combat` → 「战斗」。`opening` 不是「探索」这类打法描述——`OpeningRoom` 是副本开场（非战斗叙事场景），而 `enter_dungeon` 固定传送到 `rooms[0]`，所以它意味着「进入副本后的**起点**」。

## 副本进行中（房间）

`DungeonRoomPage` 是**房间类型的共同框架**，只放所有房间都相同的东西；房间专属内容留给按 `room.type` 分发的子视图（目前只有 `opening` 有，`combat` 未实现）。**这一层要克制**：往上加的东西必须真的适用于每一种房间。

- **数据**：当前房间 `GET /api/dungeons/v1/{user}/{game}/room`（只给房间，不含副本本体）；运行中的副本 `GET .../state`（「副本信息」用它展示进度）。两个查询各管一件事。
- **标题 = 副本名 (当前/总数) 房间名**，如「荒村义庄 (1/2) 义庄前院」。副本名与进度来自 `/state`，房间名来自 `room.stage.name`（副本房间与场景一一对应，模型与 `StageComponent` 上都是固定的）；`/state` 还没回来时先只显示房间名，不把标题卡在「加载中」。
- **顶部动作区**：目前三个按钮。「副本信息」= `DungeonInfoDialog`（整体设定 / 房间 / 敌人 + **进度**）；「叙事」= `NarrativeButton`（与家园页同一个组件，见下）；「离开副本」= 回家园。**不提供「返回副本总览」**：按游戏逻辑，离开副本就是回家园，副本进行中也没有别的去处。
- **进度不另传参数**：`current_room_index` 就是副本模型自身的字段——静态副本（磁盘 JSON）恒为 `-1`，进行中才 `>= 0`，所以同一个浮窗给总览页与房间页用都不会误标（「第 N / M 间」与房间上的「当前所在」）。
- **离开副本是任务接口**：`POST /api/dungeon/exit/v1/` 只返回 `job_id`，而「回家」发生在**任务内部**（队伍被传回家园场景、`PartyMemberComponent` 摘掉、满血恢复、`teardown_dungeon` 把副本重置回空副本）。所以界面是「触发 → 按钮变『退出中…』并禁用 → 等终态 → 跳家园页」，**不是**点了就跳；跳转用 `replace`，副本已不存在，返回键不该回到这一屏。
- **离开副本按 `room.type` 分支**（服务端 `09674f13` 起）：开场房间未完成初始化时后端会 409，所以 `opening && !initialized` 时**直接禁用**并写明原因；战斗房间不预判（战斗未结束退出由后端拦），错误原样显示。没有进行中的房间时 `/room` 返回 404，页面显示后端那句话，并给一个「← 返回家园」的出口。

**「叙事」为什么在共同框架里**：会话消息（`GET /api/session_messages/v1/.../since`）是**会话级**资源——本局所有事件，不是某个房间产生的。战斗房间一样会追加叙事，所以入口属于共同框架，不能塞进 `OpeningRoomPanel`。

- **入口只有一个实现**：`features/session/NarrativeButton`，家园页与副本房间页共用（「已看 / 总共」计数、未读高亮、`NarrativeOverlay` 都在里面）。
- **未读基线跨屏存活**：已看到第几条存在模块级的 `features/session/unreadBaselines`（按 `sessionKey(user, game)` 隔离），不随路由卸载。所以「进副本 → 打一会儿 → 回家园」后，副本期间产生的事件在家园页仍显示为未读。
- **不落 localStorage**：刷新页面即重新建立基线（当前开发阶段有意为之）；基线只在内存里，若将来要跨刷新记住，再换存储层，`useUnreadCount` 的调用方不用改。

### 开场房间（`room.type === "opening"`）

房间主体就是**准备**，对应 TUI 的 `/init` `/generate-spoils` `/pick-card` `/next`：`初始化开场 → 生成奖励 → 3 选 1 挑卡 → 进入下一关`。页面顺序是「环境叙述 → 动作按钮 → 队伍」。

- **「队伍」是横排角色卡**（不再是一人一段）：卡上点角色名开 `ActorInfoDialog`、点「查看牌组」开 `DeckDialog`。顺序沿用后端给的队伍顺序（玩家在前），横排卡片就是「队伍站位」的 UX 雏形。副本里 `ActorInfoDialog` 传 `costumeEnabled={false}`——家园接口在副本进行中会被拒，所以不展示时装入口。
- **奖励渐进式披露**：候选**不**摊在页面上；某成员有 `SpoilsComponent` 时，其角色卡上多一个「奖励」按钮，点开 `SpoilsDialog` 才看到候选卡（**竖排**，每张一个「挑选」）。与「先看到角色、再看到奖励卡」的流程一致。

- **按钮只出现「当前该做的那一步」**：初始化后换成「生成奖励」；「进入下一关」常驻。
- **初始化自动跑一次**：进入开场房间后，若 `room.initialized === false` 就自动发一次初始化任务（按房间标识做一次性 guard，StrictMode 下不会双发）；失败**不自动重试**，把「初始化开场」按钮留给玩家手动重试。这是服务端 `09674f13` 的硬前置：未初始化时不允许推进 / 退出。
- **环境叙述是固定区**：`EnvironmentComponent.narrative` 放在动作按钮**上方**，**始终占位**（加载中 / 空也保留高度），避免下方按钮与队伍准备跳动。只给 opening——战斗房的环境文本会不停变化，且流程中常无意义。
- **进入下一关要确认，且未初始化时点不开**：推进不可逆，确认框列出「下一间（名字 + 类型）」与奖励状态。奖励**只提示、不阻止**（后端不要求领完奖励），但初始化是硬前置，未初始化时按钮直接禁用、给出原因。
- **读写性质不同**：`初始化` / `生成奖励` / `挑卡` 是**任务接口**（走 `src/api/useJobAction.ts`），`进入下一关` 是**同步**接口（`useAdvanceStage`）。读全部走 GET，而且**不需要任何后端新增接口**：奖励（`SpoilsComponent`）与牌组（`DeckComponent`）由 `group?all_of=PartyMemberComponent` + 一次 `details` 拿到（`useOpeningParty`），场景环境叙述用 `useStageEntity`。
- **挑卡不做二次确认**：领卡在「奖励」浮窗里完成，防误触靠卡片上的显式「挑选」按钮（与名单的「加入 / 移出」同一套心智）。领卡是**按成员各自算的**（每人一个 `SpoilsComponent`）：领完把该组件标记为 `claimed=true`（候选保留供回看），组件本身作为「已生成」守卫保留。
- **每个开场房只生成一次**：后端的幂等守卫看「有没有人还持有 `SpoilsComponent`」；领取后组件仍保留（`claimed=true`），所以「生成奖励」不会再出现。离开副本时该组件随 `PartyMemberComponent` 一并清理。
- **卡牌展示只有一份实现**：`features/cards`（`readCard` / `CardItem`），与 `features/items` 同构——`Card` 也不在 OpenAPI 里（藏在 `ComponentSerialization.data`），所以手写类型 + 运行时逐字段校验。卡牌名**不走 `displayName`**：后端牌名就是叙事化的牌名，不带 `类型.` 前缀。
- **进入下一关要确认**：推进不可逆，确认框列出「下一间（名字 + 类型）」与奖励状态。奖励**只提示、不阻止**；初始化已由按钮禁用把关（见上）。
- **不走家园那套**：副本进行中家园接口一律被拒，所以这一屏没有道具管理（背包在家园页看），也不提供「返回副本总览」。
